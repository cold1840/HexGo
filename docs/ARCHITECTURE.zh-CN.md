# HexGo 架构

## 目的

本文档定义 HexGo 首个可玩版本的预期边界，用于指导后续代码组织；它不表示当前最小应用已经实现了这些组件。

核心架构规则是：

> 完整游戏规则必须实现为确定且与平台无关的 Rust 逻辑。Bevy 可以使用规则逻辑，但不能定义规则。

## 分层

### 1. 领域层

领域层负责全部规则概念，不依赖 Bevy、渲染、输入设备、操作系统服务或真实时间。

职责包括：

- 将棋盘表示为明确的顶点和边组成的图；
- 表示空、黑棋和白棋三种顶点状态；
- 记录行棋方、连续 Pass 次数、贴目、游戏状态和历史棋盘局面；
- 查找棋串、不重复的气、相连空域和领地；
- 严格按照规则指定顺序验证并执行落子；
- 处理提子、自杀检查和全局同形禁着；
- 处理 Pass 和认输；
- 计算最终面积分数和结果。

领域操作应返回结构化结果和错误，不应显示文本或触发 UI 效果。非法行动必须保持状态不变。棋盘拓扑和规则应支持确定性的相等比较与哈希，以记录历史局面。

### 2. 应用层

应用层负责协调对局流程，但不定义规则。它将用户意图转换为领域操作，并向展示层发布结果。

职责包括：

- 根据已验证配置创建对局；
- 提交落子、Pass 和认输命令；
- 提供合法行动结果、提子、回合变化、分数和游戏结束状态；
- 在对应功能实现后协调新对局、重新开始、存档和回放流程。

应用层不得重复实现提子、计分或合法性逻辑。

### 3. 展示层

Bevy 展示层负责渲染和交互：

- 绘制六边形铺砖、可落子顶点、棋子、高亮和 UI；
- 将鼠标或键盘输入转换为应用命令；
- 显示合法性反馈、当前回合、Pass 状态、分数和结果；
- 对领域结果添加动画，但不得改变其含义。

Bevy ECS 组件可以引用稳定的领域标识符，但领域类型不能依赖 Bevy ECS trait 才能运行。

### 4. 适配器

持久化、回放格式、分析以及未来的 AI 或网络集成都属于应用层和领域层外围的适配器。它们必须使用与本地人类玩家相同的公共游戏命令，不能绕过合法性检查。

## 数据流

```text
玩家输入
    ↓
Bevy 展示层
    ↓
应用命令
    ↓
领域验证和状态转换
    ↓
结构化结果或错误
    ↓
应用事件
    ↓
Bevy 展示层更新
```

渲染结果绝不能成为占用状态、相邻关系、回合顺序或计分的真相来源。

## 规则不变量

- 每条边连接两个存在的顶点，相邻关系必须对称。
- 一个顶点只有一种状态：空、黑棋或白棋。
- 棋串、气和空域只根据图的边推导。
- 检查新落子所属棋串前，必须先移除对方所有零气棋串。
- 被拒绝的行动不改变状态，也不消耗回合。
- Pass 不受同形禁着限制；正常落子会重置连续 Pass 次数。
- 全局同形禁着使用的局面历史只包含棋盘占用状态，不包含行棋方。
- 连续两次 Pass 后留在棋盘上的棋子，在面积计分时均视为存活。

## 测试策略

领域测试应使用小型、明确的图结构测试数据，而不是 Bevy scene。测试必须覆盖图边界、棋串合并、共享气、同时提子、先提子后判断自杀、拒绝自杀、全局同形禁着、Pass、认输、空域所有权、中立区域、双活的计分结果、贴目，以及非法行动被原子性拒绝。

应用层测试应验证命令顺序和产生的结果。可玩 UI 完成后，展示层可以使用针对性的 Bevy system 测试和端到端交互检查。

## 依赖方向

依赖只能指向内层：

```text
展示层与适配器 → 应用层 → 领域层
```

领域层不得导入外层。新增依赖需要明确批准；标准库或现有依赖足够时，不应增加新依赖。

## 延后决定

具体模块名称、序列化文件格式、棋盘尺寸预设、网络协议和 AI 算法将在对应路线图阶段开始时确定。所有方案都必须保持本文档的边界和不变量。
